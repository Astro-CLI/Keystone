# פרק 4: אוטומציות ותכנות במהלך הפרויקט

## 4.1 הקדמה

בשלב המימוש של תשתית הענן של SOYMSA בסביבת Packet Tracer, עלתה אותה בעיה קלאסית: תצורה ידנית של עשרות התקנים אינה סקיילבילית. הקלדה חוזרת של פקודות CLI לכל נתב, מתג, חומת אש ושרת הייתה גוזלת זמן רב ומייצרת טעויות אנוש.

בשלב הראשון פותח פתרון מבוסס Python ליצירת פקודות IOS (Option A). בהמשך, לאחר מחקר נוסף, הצלחנו להפעיל JavaScript בתוך Packet Tracer ולעבוד עם מודולי הסקריפט הרשמיים (PT Scripting / PTBuilder). תגלית זו שינתה מהותית את כיוון הפרויקט: במקום להילחם בפורמט בינארי סגור של `.pkt`, ניתן לבצע אוטומציה מבפנים דרך הממשק הרשמי של Packet Tracer (Option C).

## 4.2 הבעיה: תצורה ידנית חוזרת ונשנית

תצורת רשת רב-התקנית כוללת רצף פעולות דומות:
- הקצאת כתובות IP לממשקים
- הפעלת פרוטוקולי ניתוב (OSPF/BGP/EIGRP)
- הגדרת שירותים (NAT, DHCP, VLAN, HSRP)
- אימות קישוריות

בביצוע ידני ב-Packet Tracer, כל שלב חזר על עצמו לכל התקן בנפרד. עבור טופולוגיה ארגונית מלאה, מדובר במאמץ גדול שאינו יעיל.

## 4.3 ארכיטקטורת הפתרון המעודכנת

האוטומציה בנויה בשלוש שכבות משלימות:

**שכבה 1 – מפענח פורמטים (`format_parser.py`)**  
תמיכה אחידה בקבצי YAML / JSON / XML באמצעות `parse_file()`.

**שכבה 2 – מחוללי תצורה לפי פרוטוקול (12 generators)**  
מחוללים ייעודיים ל-OSPF, BGP, EIGRP, מסלולים סטטיים, ASA, NAT, VLAN, DHCP, HSRP, SSH, תכנון IP ו-CIDR.

**שכבה 3 – אוטומציית Packet Tracer מבוססת JavaScript (Option C)**  
שימוש במודול הסקריפטים של Packet Tracer ליצירת טופולוגיה ישירות מתוך הסימולטור, במקום יצירה חיצונית של קובץ בינארי.

## 4.4 Option A: `topology_composer.py` ככלי בסיס יציב

`topology_composer.py` נשאר כלי מרכזי: המשתמש מגדיר טופולוגיה בקובץ YAML/JSON/XML, ומקבל קובץ פקודות IOS מוכן להרצה.

דוגמת הרצה:

```bash
python3 topology_composer.py --file network.yaml --output commands.txt
```

הכלי מספק תהליך אמין ליצירת קונפיגורציה, ומקטין משמעותית עבודה ידנית.

## 4.5 Option B: יצירת `.pkt` בינארית ישירה (סטטוס)

ניסיון Option B (`pt_file_builder.py`) הצליח ברמת מבנה הקובץ (header/payload/compression), אך נכשל בפתיחה ב-PT 8.2.2 עקב מנגנון הצפנה/ולידציה קנייני שאינו מתועד ציבורית בגרסאות חדשות.

מסקנה מעשית: Option B נשאר מסלול מחקרי ואינו מסלול הייצור המומלץ.

## 4.6 הפריצה: Option C – JavaScript + PT Scripting Modules

הפתרון שהבשיל בפועל הוא Option C: שימוש ביכולות הסקריפט הרשמיות של Packet Tracer דרך JavaScript.

**נקודות מפתח:**
- עבודה דרך ממשק הסקריפטים בתוך Packet Tracer
- גישה לאובייקטי IPC כגון `ipc.network()` ו-`ipc.appWindow().getActiveFile()`
- יצירת התקנים באמצעות `duplicateDevice(...)`
- מיקום התקנים באמצעות `moveToLocationCentered(...)`
- שמירה לקובץ `.pkt` דרך מנגנון השמירה הטבעי של Packet Tracer

כלומר, במקום לייצר קובץ `.pkt` מוצפן מבחוץ, האוטומציה פועלת מתוך Packet Tracer עצמו – בצורה תואמת למנגנון הנתמך של המוצר.

## 4.7 תיעוד וכלים רלוונטיים (מקורות הפרויקט)

בפרויקט קיים תיעוד ייעודי ומעודכן ל-Option C:
- `Automation/docs/README_OPTION_C.md` — מסמך כניסה ל-Option C
- `Automation/docs/OPTION_C_PTBUILDER.md` — תהליך PTBuilder והמרה מטופולוגיה לסקריפט
- `Automation/docs/OPTION_C_COMPLETE_DOCUMENTATION.md` — תיעוד API מלא ודוגמאות
- `Automation/docs/API_QUICK_REFERENCE.md` — דף עזר מהיר לפקודות/API
- `Automation/docs/TROUBLESHOOTING_GUIDE.md` — תקלות נפוצות ופתרונות

קבצי יישום מרכזיים:
- `Automation/main.js` – סקריפט JavaScript להרצה ישירה בתוך Packet Tracer
- `Automation/tools/pt_scriptable_builder.py` – מחולל שימושי עיקרי שמייצר קוד `addDevice/addLink` לתרחיש Builder Code Editor
- `Automation/tools/pt_scriptable_builder_real.py` – וריאנט ניסיוני/מתקדם שמכוון ל-IPC Scripting Module (Extensions → Scripting) לצורך בדיקות API ישירות

## 4.8 טופולוגיות לדוגמה

הפרויקט כולל טופולוגיות דוגמה לשימוש מיידי:
- `Automation/examples/simple_topology.yaml`
- `Automation/examples/example_topology.yaml`
- `Automation/examples/complex_topology.yaml`
- `Automation/examples/small_office_topology.yaml`

קבצים אלה משמשים הן ל-Option A (פקודות CLI) והן לתרחישים של Option C.

## 4.9 הישגים מעודכנים

במהלך הפרויקט הושגו התוצאות הבאות:
- מפענח אחיד לשלושה פורמטים (`format_parser.py`)
- 12 מחוללי תצורה ייעודיים
- כלי יציב ליצירת פקודות IOS (`topology_composer.py`)
- מסלול JavaScript פעיל ואופרטיבי בתוך Packet Tracer (Option C)
- תיעוד מלא ל-Option C כולל API, Quick Reference ו-Troubleshooting
- 33 בדיקות יחידה בפרויקט (בפועל עוברות בהצלחה)
- סט טופולוגיות דוגמה מוכן לשימוש

## 4.10 ניתוח: מה עובד ומה מוגבל

**מה עובד היטב:**
- Option A: הפקת קונפיגורציה מלאה ומהירה
- Option C: יצירה/שינוי טופולוגיה מתוך Packet Tracer באמצעות JavaScript
- תמיכה עקבית ב-YAML/JSON/XML לאורך הכלים
- תיעוד ישים למשתמשים ולמפתחים

**מגבלות ידועות:**
- Option B אינו פתרון ייצור לגרסאות PT מודרניות
- חלק מפעולות ה-API ב-PT מוגבלות/תלויות גרסה
- במקרים מסוימים עדיין נדרשת השלמה ידנית של קונפיגורציות CLI

## 4.11 המלצות וסיכום

המלצת העבודה המעודכנת:
1. להשתמש ב-Option A ליצירת קונפיגורציות CLI אמינות ומהירות.
2. להשתמש ב-Option C כדי לאוטומט יצירה/פריסה של טופולוגיה ישירות בתוך Packet Tracer.
3. לראות ב-Option B מסלול מחקרי בלבד בשלב זה.

בשורה התחתונה, שילוב Option A + Option C מספק פתרון אוטומציה פרקטי וחזק: גם יצירת טופולוגיה מהירה, וגם יצירת קונפיגורציות בהיקף רחב – עם חיסכון משמעותי בזמן וצמצום טעויות אנוש.
